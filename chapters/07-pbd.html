Position-Based Dynamics

Thirty particles, twenty-nine constraints, and a loop that never explodes.

The previous chapter enforced one constraint at a time by moving positions, and hinted that several constraints sharing particles need several passes. That idea, made into a complete simulator, is position-based dynamics (PBD), introduced by Matthias Müller, Bruno Heidelberger, Marcus Hennix and John Ratcliff in 2007. It became the workhorse of real-time cloth, ropes and soft bodies in games because it is short, fast and very hard to blow up.

In this chapter you will build PBD for a hanging rope: the algorithm, the distance constraint with inverse masses, pinned and dragged particles, two ways to run the constraint loop (Gauss-Seidel and Jacobi), and the stiffness parameter. Then you will measure PBD's big flaw: the rope's stiffness is not a property of the rope. It depends on how many iterations you run and how large your time step is. Understanding that flaw precisely is the motivation for the next chapter.

The algorithm

PBD keeps, for every particle $i$, a position $\mathbf{x}_i$, a velocity $\mathbf{v}_i$ and an inverse mass $w_i$. Each time step of size $h$ does four things:

  1. Apply external forces to the velocities: $\mathbf{v}_i \leftarrow \mathbf{v}_i + h\,w_i\,\mathbf{f}_i^\text{ext}$ (for gravity, $\mathbf{v}_i \leftarrow \mathbf{v}_i + h\,\mathbf{g}$).
  2. Predict positions: $\mathbf{p}_i = \mathbf{x}_i + h\,\mathbf{v}_i$. The predictions ignore all the constraints.
  3. Project the constraints: loop $n$ times over every constraint, moving the predicted positions $\mathbf{p}_i$ to satisfy it.
  4. Update: $\mathbf{v}_i = (\mathbf{p}_i - \mathbf{x}_i)/h$, then $\mathbf{x}_i = \mathbf{p}_i$.

That is the whole method. Internal forces never appear: everything that holds the object together is a constraint, and constraints act on positions. Notice that step 4 is what makes it dynamics and not just geometry. Because velocities come from position changes, a constraint that pulls a particle back also changes its velocity, so momentum flows through the rope exactly as it would through real tension.

function step(h) {
  for (const p of particles) {                       // 1 and 2: forces, then predict
    p.prev = V.copy(p.x);
    if (p.w === 0) continue;
    p.v = V.v(p.v.x, p.v.y - gravity * h);
    p.x = V.addScaled(p.x, p.v, h);                  // p.x now holds the prediction
  }
  for (let it = 0; it < iterations; it++) {          // 3: project, n times
    solveGaussSeidel(k);
  }
  for (const p of particles) {                       // 4: velocities from positions
    p.v = V.scale(V.sub(p.x, p.prev), 1 / h);
  }
}

In code it is convenient to store the prediction in x itself and keep the old position in prev, as here. The paper writes $\mathbf{p}$ for the prediction and $\mathbf{x}$ for the old position; same thing.

The distance constraint, with inverse masses

A rope is a row of particles in which each neighbouring pair must stay a distance $d$ apart:

$$C(\mathbf{p}_1, \mathbf{p}_2) = |\mathbf{p}_1 - \mathbf{p}_2| - d = 0.$$

Let $\mathbf{n} = (\mathbf{p}_1 - \mathbf{p}_2)/|\mathbf{p}_1 - \mathbf{p}_2|$. The gradients are $\nabla_{\mathbf{p}_1} C = \mathbf{n}$ and $\nabla_{\mathbf{p}_2} C = -\mathbf{n}$. We want corrections $\Delta\mathbf{p}_1$, $\Delta\mathbf{p}_2$ that satisfy three conditions:

  1. they fix the constraint to first order: $C + \nabla_{\mathbf{p}_1}C\cdot\Delta\mathbf{p}_1 + \nabla_{\mathbf{p}_2}C\cdot\Delta\mathbf{p}_2 = 0$;
  2. they point along the gradients, so the constraint does no work in the directions it allows: $\Delta\mathbf{p}_i = \lambda\,w_i\,\nabla_{\mathbf{p}_i}C$;
  3. they are weighted by inverse mass, so heavy particles move less and the centre of mass stays put ($m_1\Delta\mathbf{p}_1 + m_2\Delta\mathbf{p}_2 = \lambda\mathbf{n} - \lambda\mathbf{n} = 0$).

Substitute the second into the first: $C + \lambda w_1 |\mathbf{n}|^2 + \lambda w_2 |\mathbf{n}|^2 = 0$, so $\lambda = -C/(w_1 + w_2)$, and

$$\Delta\mathbf{p}_1 = -\frac{w_1}{w_1 + w_2}\,\bigl(|\mathbf{p}_1 - \mathbf{p}_2| - d\bigr)\,\mathbf{n}, \qquad \Delta\mathbf{p}_2 = +\frac{w_2}{w_1 + w_2}\,\bigl(|\mathbf{p}_1 - \mathbf{p}_2| - d\bigr)\,\mathbf{n}.$$

For equal masses each particle moves half the error toward the other. If particle 2 is pinned ($w_2 = 0$), particle 1 moves the full error and particle 2 stays still. If both are pinned, nothing can move and the constraint is skipped. This is the same projection you wrote in chapter 06, now returning the two corrections instead of applying them, so that both solvers below can share it:

function distanceCorrection(c, k) {
  const pa = particles[c.a], pb = particles[c.b];
  const d = V.sub(pa.x, pb.x);
  const len = V.len(d);
  const wsum = pa.w + pb.w;
  if (wsum === 0 || len < 1e-12) return null;
  const C = len - c.rest;
  const s = -k * C / (wsum * len);       // lambda / len, so that s * d = lambda * n
  return { ax: pa.w * s * d.x, ay: pa.w * s * d.y, bx: -pb.w * s * d.x, by: -pb.w * s * d.y };
}

(Ignore $k$ for now; with $k = 1$ it is the full projection.)

Attachments and dragging

The pinned end of the rope is a particle with $w = 0$. The update skips it, every constraint correction leaves it alone, and the rope hangs from it. The paper calls this an attachment, and it is one of the nicest features of the method: to fix a point, you set one number.

Dragging with the mouse uses the same trick. While you hold a particle its inverse mass is set to zero and its position is set to the mouse at each step; the constraints then pull the rest of the rope along, and when you let go it gets its mass back, with whatever velocity its last move implies. A particle that is "infinitely heavy for now" is the safest way to impose motion in PBD: nothing in the solver can fight it.

Gauss-Seidel and Jacobi

Step 3 says "loop over every constraint", but there are two quite different ways to do that.

Gauss-Seidel projects one constraint at a time, in place. The second constraint sees the positions already corrected by the first, and so on along the rope. Information travels fast: a correction at the top can reach the bottom in a single sweep. But the result depends on the order of the constraints, and the loop is inherently sequential, because each projection needs the previous one's result.

function solveGaussSeidel(k) {
  for (const c of constraints) {
    const corr = distanceCorrection(c, k);
    if (!corr) continue;
    const pa = particles[c.a], pb = particles[c.b];
    pa.x = V.v(pa.x.x + corr.ax, pa.x.y + corr.ay);   // applied immediately
    pb.x = V.v(pb.x.x + corr.bx, pb.x.y + corr.by);
  }
}

Jacobi computes every constraint's correction from the same positions, adds them up per particle, and applies them all at the end of the pass. Every constraint is independent, so on a GPU each one can run on its own thread. There is a catch. A particle in the middle of a rope belongs to two constraints, and if the rope is stretched, both try to fix the same error by moving it. Applying both corrections in full moves it twice as far as needed, and the solver overshoots and oscillates. The standard fix, popularised by Macklin, Müller, Chentanez and Kim in their 2014 paper on unified particle physics, is to average: divide each particle's summed correction by the number of constraints that touched it,

$$\Delta\mathbf{p}_i = \frac{\omega}{n_i}\sum_{c \ni i} \Delta\mathbf{p}_i^{(c)},$$

where $n_i$ is that count and $\omega$ is an over-relaxation factor between 1 and 2 that wins back some of the speed averaging gives away. (Averaging is safe but cautious. With $\omega$ of 1.8 or more and a single iteration per step, the demo's rope blows up.)

Try both in the demo. With 10 iterations per step and the rope hanging from one end, Gauss-Seidel leaves it 5.3 % longer than its rest length; Jacobi leaves it 17 % longer, and 13 % with $\omega = 1.5$. Jacobi converges more slowly per iteration because corrections spread only one constraint per pass. Its advantage is parallelism, not speed per iteration: on a GPU, a hundred Jacobi iterations can be cheaper than ten sequential Gauss-Seidel ones.

The stiffness parameter

Not everything should be rigid. PBD makes a constraint softer by scaling each correction by a stiffness $k \in [0, 1]$: with $k = 1$ the projection fixes the whole error, with $k = 0.5$ half of it. That is the $k$ in distanceCorrection.

The trouble is that the correction is applied once per iteration. Take a single constraint with nothing else around it. After one projection a fraction $1 - k$ of its error remains; after $n$ projections, $(1 - k)^n$. So the fraction actually removed per time step is

$$k_\text{eff} = 1 - (1 - k)^n.$$

With $k = 0.5$ and 10 iterations, $k_\text{eff} = 0.999$: a "half-stiff" constraint behaves as if fully rigid. The paper proposes a correction: use $k' = 1 - (1 - k)^{1/n}$ in each iteration, so that $n$ iterations multiply up to $1 - (1 - k')^n = k$. For $k = 0.5$ and $n = 10$, $k' = 0.067$. In the demo, tick the box and set $k = 0.9$. Without the correction, the hanging rope stretches by 12.6 %, 2.9 % and 0.64 % at 5, 20 and 80 iterations. With it, by about 48 % in all three cases: the stiffness no longer depends on the iteration count. Now set two steps per frame. The stretch drops to 14 %. The stiffness still depends on the time step.

The big flaw: stiffness is a solver setting

Set $k = 1$ again: every constraint asks to be perfectly rigid. Now vary the iterations and watch the stretch readout once the rope has settled.

With both ends pinned 2 m apart, the exact sag of an inextensible 2.32 m rope (a catenary) is 0.516 m. PBD approaches it only as the iterations go up. At 10 iterations the bridge sags 0.60 m and the hanging rope is 5 % too long. A rope that "should be" inextensible behaves like a rubber band, and how rubbery depends on a performance setting.

Why? Every step, gravity moves every particle down by $h^2 g$ in the prediction, and a few iterations cannot fully undo that across 29 links. Long, smooth errors (the whole rope being slightly too long) are the slowest for a local solver to remove, because each projection only knows about its own two particles. The rope settles where the error the solver fails to remove each step balances what gravity adds. The table shows the consequence: for 10 or more iterations, the stretch times the iteration count stays between 40 and 53, so the stretch is roughly inversely proportional to $n$. The time step enters squared, because gravity's push per step is $h^2 g$: at 10 iterations, 1, 2, 4 and 8 steps per frame give stretches of 5.3 %, 1.26 %, 0.36 % and 0.13 %, close to a factor 4 for each halving of $h$.

So a PBD rope behaves like a spring whose stiffness grows roughly like $n/h^2$. Change the frame rate, or lower the iteration count to save time on a slow device, and the material changes. You cannot ask PBD for "a rope of stiffness 5000 N/m", because PBD's stiffness has no units: it is a number between 0 and 1 whose meaning depends on $n$ and $h$. That is the big flaw, and the reason for the next chapter.

Substeps beat iterations. Compare equal work: 20 iterations in one step stretch the rope by 2.3 %, but two steps of 10 iterations each stretch it by 1.26 %; 50 iterations give 0.84 %, while four steps of 10 (40 projections in total) give 0.36 %. Splitting the frame into smaller steps attacks the $h^2$ directly. This observation grew into a method of its own, Small Steps.

None of this makes PBD bad. With Gauss-Seidel it is very hard to blow up (positions are projected, never accelerated by huge forces, and the velocity update removes energy rather than adding it), it handles collisions and attachments with the same machinery, and it is simple. But if you need a material with a physical stiffness that holds across time steps and iteration counts, you need one more ingredient: XPBD replaces $k$ with a compliance $\alpha$ in physical units (metres per newton) and adds a little bookkeeping so the result no longer depends on $n$ and $h$.

Solution 
function solveJacobi(k) {
  dx.fill(0); dy.fill(0); counts.fill(0);
  for (const c of constraints) {
    const corr = distanceCorrection(c, k);
    if (!corr) continue;
    dx[c.a] += corr.ax; dy[c.a] += corr.ay; counts[c.a]++;
    dx[c.b] += corr.bx; dy[c.b] += corr.by; counts[c.b]++;
  }
  for (let i = 0; i < N; i++) {
    if (counts[i] === 0) continue;
    const p = particles[i];
    p.x = V.v(p.x.x + omega.value * dx[i] / counts[i], p.x.y + omega.value * dy[i] / counts[i]);
  }
}

At 10 iterations Jacobi leaves 17 % stretch against Gauss-Seidel's 5.3 %; at 100, 1.7 % against 0.40 %. $\omega = 1.5$ improves Jacobi to 13 % and 1.2 %, though at a single iteration it makes things worse. Without the averaging, an interior particle receives two full corrections for one error, which is the same as averaging with $\omega = 2$, the edge of stability: at one iteration per step the rope blows up, while at 10 or more it survives.

the 2007 PBD paper in our notation

Müller, Heidelberger, Hennix and Ratcliff, Position Based Dynamics (VRIPHYS 2006, then the Journal of Visual Communication and Image Representation, 2007). Their section on position-based simulation lists the algorithm above with $\mathbf{x}_i$ for positions, $\mathbf{p}_i$ for predictions, $w_i$ for inverse masses and solverIterations for our $n$. Their constraint-projection subsection derives the general correction $\Delta\mathbf{p}_i = -s\,w_i\nabla_{\mathbf{p}_i}C$ with $s = C / \sum_j w_j|\nabla_{\mathbf{p}_j}C|^2$, which is our $\lambda = -s$, and works the distance constraint as the example; the same subsection introduces the stiffness $k$ and the $k' = 1 - (1 - k)^{1/n_s}$ correction. Attachments ($w = 0$) and a damping scheme that removes only non-rigid relative motion have their own short subsections. The paper solves constraints sequentially; the averaged Jacobi variant came later, and the PB-MPM paper's solver is a descendant of that parallel line: its iterations, too, run in parallel over particles and grid nodes.

Summary

  • PBD: apply external forces, predict positions, project constraints $n$ times, set velocities from the position change.
  • The distance constraint moves its two particles along $\pm\mathbf{n}$ by $w_i/(w_1 + w_2)$ of the error each, conserving momentum. Pinned and dragged particles have $w = 0$.
  • Gauss-Seidel projects in place, converges faster per iteration, and depends on order. Jacobi accumulates corrections, needs averaging (optionally over-relaxed by $\omega$), and parallelises.
  • The stiffness $k$ acts per iteration: $k_\text{eff} = 1 - (1-k)^n$. The $k'$ correction removes the iteration dependence for one constraint, not the time-step dependence.
  • Even at $k = 1$, the apparent stiffness of a PBD object grows roughly like $n/h^2$: material behaviour depends on solver settings. XPBD fixes this.

Collision Detection

Finding out who touches whom, quickly, and without letting anything slip through.

Every simulation so far has lived in empty space, apart from a floor we checked with one line: if (y < 0). Real scenes are full of things. A rope drapes over a pulley, a thousand marbles pour down a ramp, a ball bounces off a wall. Before any of these can push on each other, the simulation has to answer a question that sounds trivial and is not: which pairs of things are touching right now, and how deeply?

Answering it well takes three ideas. A way to describe the shape of the world so that "how far am I from the nearest wall, and in which direction" is one function call. A way to avoid testing every particle against every other, because with a few thousand particles that alone would eat the whole frame. And a defence against fast objects that move so far in one step that they jump clean over a thin wall without ever overlapping it.

By the end of this chapter you will be able to write signed distance functions for the common shapes and combine them into a scene, collide particles against that scene, find particle-particle contacts in linear time with a spatial hash, and predict the speed at which a ball will tunnel through a wall.

Two phases: cheap and approximate, then exact

Collision detection is almost always split in two.

The broad phase throws away pairs that cannot possibly touch, using something cheap: a bounding box around each object, a grid, a sorted list. Its output is a short list of candidate pairs. It is allowed to be pessimistic (some candidates turn out not to touch) but never optimistic: it must not lose a pair that does touch.

The narrow phase takes each candidate pair and does the exact test. If the two shapes overlap, it produces the contact data the solver needs: a unit normal $\mathbf{n}$ (the direction in which to push them apart), a penetration depth $d$ (how far), and, for rigid bodies, a contact point. Everything in the next chapter, contact constraints and friction, runs on this data.

For particles against a static scene the broad phase is often skipped entirely: if the scene is described by a single function that returns the distance to the nearest surface, each particle asks it once. That function is the first idea of this chapter.

Signed distance functions

A signed distance function (SDF) $\phi(\mathbf{x})$ returns the distance from the point $\mathbf{x}$ to the nearest surface of a shape, with a sign: positive outside, negative inside, zero exactly on the surface. That one number answers "am I inside?" (the sign) and "how deep?" (the magnitude). Its gradient answers the third question, "which way is out?": for a true distance function the gradient $\nabla\phi$ has length 1 everywhere and points away from the nearest surface, so it is the contact normal.

Here are the shapes you will need, each a few lines.

Circle of centre $\mathbf{c}$ and radius $R$: the distance to the centre, minus the radius.

$$\phi_{\text{circle}}(\mathbf{x}) = |\mathbf{x} - \mathbf{c}| - R.$$

Half-plane through a point $\mathbf{a}$ with unit normal $\mathbf{n}$ pointing into free space (a floor, a wall): the distance along the normal.

$$\phi_{\text{plane}}(\mathbf{x}) = (\mathbf{x} - \mathbf{a})\cdot\mathbf{n}.$$

Box with half extents $(h_x, h_y)$, centred at the origin and aligned with the axes (for a rotated box, first rotate the point into the box's frame). Let $d_x = |x| - h_x$ and $d_y = |y| - h_y$, the distances outside each pair of faces. Outside the box the nearest point is on a face or a corner; inside, the nearest face is the one we are closest to:

$$\phi_{\text{box}} = \big|\big(\max(d_x, 0),\, \max(d_y, 0)\big)\big| + \min\big(\max(d_x, d_y),\, 0\big).$$

The first term is zero inside and the second is zero outside, so the formula works everywhere. It is worth checking at one point: at $(0, 0)$ in a box of half extents $(0.4, 0.02)$, $d_x = -0.4$, $d_y = -0.02$, and $\phi = -0.02$: two centimetres inside, through the nearer, long face.

Capsule: all points within radius $r$ of a segment from $\mathbf{a}$ to $\mathbf{b}$. A rope segment, a finger, a pill-shaped obstacle. Its SDF needs the closest point on the segment, which deserves its own section.

The closest point on a segment

Any point on the line through $\mathbf{a}$ and $\mathbf{b}$ can be written $\mathbf{a} + t(\mathbf{b} - \mathbf{a})$, with $t = 0$ at $\mathbf{a}$ and $t = 1$ at $\mathbf{b}$. The closest point on the line to $\mathbf{x}$ is the orthogonal projection:

$$t^* = \frac{(\mathbf{x} - \mathbf{a})\cdot(\mathbf{b} - \mathbf{a})}{|\mathbf{b} - \mathbf{a}|^2}.$$

For a segment, clamp $t^*$ to $[0, 1]$: beyond either end, the closest point is that end. Then the capsule is a circle swept along the segment:

$$\mathbf{q} = \mathbf{a} + \operatorname{clamp}(t^*, 0, 1)\,(\mathbf{b} - \mathbf{a}), \qquad \phi_{\text{capsule}}(\mathbf{x}) = |\mathbf{x} - \mathbf{q}| - r.$$

This little projection is the most reused function in collision detection. It is your first exercise.

Building a scene: union is min

If you are outside two shapes, the nearest surface is the nearer of the two. If you are inside either, you are inside the union. Both facts say the same thing:

$$\phi_{A \cup B}(\mathbf{x}) = \min\big(\phi_A(\mathbf{x}),\, \phi_B(\mathbf{x})\big).$$

So a whole scene is a chain of Math.min calls:

function sceneSdf(px, py) {
  let d = sdHalfPlane(px, py, 0, 0, 0, 1);                 // floor
  d = Math.min(d, sdHalfPlane(px, py, -1, 0, 1, 0));       // left wall
  d = Math.min(d, sdBox(px, py, -0.45, 0.95, 0.42, 0.02, -0.3));   // a slope
  d = Math.min(d, sdCapsule(px, py, -0.25, 0.3, 0.15, 0.22, 0.05));
  d = Math.min(d, sdCircle(px, py, 0.62, 0.0, 0.14));
  return d;
}

One caveat: the minimum of true distance functions is exact outside, but slightly wrong inside where two shapes overlap (the inside distance should be to the surface of the union, not of one piece). For collision response that rarely matters, because particles live near the surface. Intersection is $\max(\phi_A, \phi_B)$ and subtraction is $\max(\phi_A, -\phi_B)$, with the same caveat.

Normals from the gradient

For simple shapes you can write the gradient by hand (for a circle it is $(\mathbf{x} - \mathbf{c}) / |\mathbf{x} - \mathbf{c}|$). For a scene built from min calls, central differences are simpler and work for any SDF you will ever write:

$$\nabla\phi \approx \frac{1}{2\varepsilon}\begin{pmatrix} \phi(x + \varepsilon, y) - \phi(x - \varepsilon, y) \\ \phi(x, y + \varepsilon) - \phi(x, y - \varepsilon)\end{pmatrix}, \qquad \mathbf{n} = \frac{\nabla\phi}{|\nabla\phi|}.$$

Four extra SDF evaluations per contact, and only for particles that are actually touching something. We normalise because the min and the finite difference both make the length a little different from 1 near edges and corners.

Particle against the scene

A particle of radius $r$ touches the scene when its centre is closer than $r$ to the surface. Its gap is $g = \phi(\mathbf{x}) - r$. A negative gap is a penetration of depth $-g$, and the fix is to move the particle that far along the normal:

$$\text{if } g < 0: \qquad \mathbf{x} \leftarrow \mathbf{x} - g\,\mathbf{n}.$$

If this looks familiar, it should: it is a position-based constraint projection from the PBD chapter, with constraint $C(\mathbf{x}) = \phi(\mathbf{x}) - r \ge 0$ and gradient $\nabla C = \mathbf{n}$. The static scene has infinite mass, so the particle takes the whole correction. The inequality is the new part: we only project when $C < 0$. The next chapter makes this precise and adds friction; for now, push out and let the PBD velocity update $\mathbf{v} = (\mathbf{x} - \mathbf{x}_{\text{prev}})/h$ turn the correction into a velocity.

Play with the demo. Hundreds of particles pour from the top left onto two slopes, a capsule and a round bumper. Tick "draw distance field" to see $\phi$ itself: blue outside, orange inside, a band every 10 cm. Notice how the bands round off around the corners of the slopes: outside a convex corner the nearest point is the corner itself, so the contours are circles.

There is no friction yet, so the heap flows like a liquid and settles flat. That is the next chapter's job. The demo runs eight substeps of one PBD pass each. Drop it to four and watch the bottom-left corner: now and then a particle squirts up the wall at more than 10 m/s. Where the flow jams into the corner, a whole chain of overlaps is resolved in one pass, and since PBD turns position corrections into velocity, the chain's accumulated correction becomes one particle's speed. Smaller steps mean smaller overlaps, which is the cure.

Particle against particle

Two particles of radius $r$ overlap when the distance between their centres is less than $2r$. With equal masses, each moves half the overlap along the line between them:

function solvePair(i, j) {
  const dx = x[j] - x[i], dy = y[j] - y[i];
  const d2 = dx * dx + dy * dy, D = 2 * radius;
  if (d2 >= D * D || d2 === 0) return;
  const d = Math.sqrt(d2), c = 0.5 * (D - d) / d;   // each takes half the overlap
  x[i] -= dx * c; y[i] -= dy * c;
  x[j] += dx * c; y[j] += dy * c;
}

Comparing squared distances first avoids a square root for the vast majority of pairs, which are not touching. The narrow phase is easy. The problem is how many pairs we hand it.

The cost of brute force

Testing every pair means $n(n-1)/2$ tests. For the demo's default 600 particles that is 179,700 tests per substep; for 2,000 it is 1,999,000. The cost grows as $O(n^2)$: double the particles, quadruple the work. Yet each particle only ever touches its immediate neighbours, about six of them in a dense pile. Almost all of those two million tests answer "no".

Switch the demo to 2,000 particles with brute force and read the "contact time". With eight substeps per frame that is 16 million pair tests per frame, and on a typical laptop it takes more than the whole 16.7 ms frame budget, spent almost entirely on saying no.

A uniform grid

Divide space into square cells of side equal to the particle diameter $2r$. A particle can only touch particles whose centres are less than $2r$ away, so they must sit in its own cell or one of the eight around it. If we can list the particles in each cell, each particle tests only the contents of a 3×3 block: a fixed amount of work per particle, and $O(n)$ in total.

How many candidates is that? In a dense hexagonal packing there are $2/\sqrt{3} \approx 1.15$ particles per area $(2r)^2$, so the 3×3 block holds about 10.4 particles including the one asking. Each pair is found from both ends, so keeping only $j > i$ leaves about five tests per particle, against $n/2$ for brute force.

A plain 2D array of cells would need to cover the whole world, and most cells would be empty. The trick that removes that limit is to hash the integer cell coordinates into a fixed-size table:

function hashCell(ix, iy) {
  const h = Math.imul(ix, 92837111) ^ Math.imul(iy, 689287499);  // two large primes, 32-bit multiply
  return Math.abs(h) % TABLE_SIZE;
}

Different cells can land in the same bucket (a hash collision), so a bucket may contain particles from a cell far away. That is harmless: the narrow phase rejects them. It only costs a few wasted tests, and a table about twice the number of particles keeps them rare. (Math.imul is a true 32-bit integer multiply, the same as int multiplication in C# or C++; a plain * in JavaScript would compute in floating point.)

Filling the table with a counting sort

We could give each bucket a growable list, but allocating lists every substep is slow and does not port to a GPU. The approach from Matthias Müller's Ten Minute Physics (tutorial 11, on finding overlaps among thousands of objects) uses two flat integer arrays and a counting sort:

  • cellEntries, of length $n$: every particle index, grouped by bucket.
  • cellStart, of length TABLE_SIZE + 1: where each bucket's group begins. Bucket $h$ owns cellEntries[cellStart[h]] to cellEntries[cellStart[h + 1] - 1].

It is filled in three passes:

  1. Count. Zero cellStart; for every particle, compute its bucket and add one.
  2. Running sum. Replace each count by the sum of the counts up to and including it. Now cellStart[h] points one past the end of bucket $h$'s group. Set the extra last entry to $n$.
  3. Insert. For every particle, decrement its bucket's entry and write the particle index there. Each bucket fills from its end backwards, and when the pass is done every cellStart[h] has been decremented by exactly its count: it now points to the start.

Work through a tiny case on paper: four buckets and particles in buckets 2, 0, 2, 3. The counts are $[1, 0, 2, 1]$, the running sums $[1, 1, 3, 4]$ plus the final 4, and after inserting (particle 0 into slot 2, particle 1 into slot 0, particle 2 into slot 1, particle 3 into slot 3) cellStart is $[0, 1, 1, 3, 4]$ and cellEntries is $[1, 2, 0, 3]$. Bucket 2 owns slots 1 and 2: particles 2 and 0. Bucket 1 is empty because its start equals the next bucket's start.

The query then loops over the nine cells around a particle:

const ix = Math.floor(x[i] / cellSize), iy = Math.floor(y[i] / cellSize);
for (let dx = -1; dx <= 1; dx++)
  for (let dy = -1; dy <= 1; dy++) {
    const h = hashCell(ix + dx, iy + dy);
    for (let k = cellStart[h]; k < cellStart[h + 1]; k++) {
      const j = cellEntries[k];
      if (j > i) solvePair(i, j);     // each pair once
    }
  }

Building costs two passes over the particles and one over the table, so the whole broad phase is $O(n)$. Switch the demo to the spatial hash, tick "draw hash cells", and hover over a particle: the purple square is its 3×3 query, orange particles are the candidates found in those buckets, red ones are real contacts. Now and then an orange particle appears far away. That is a hash collision, rejected by the distance test.

Rebuild every substep, and pick the cell size from the query radius. The hash is only valid for the positions it was built from. Particles move less than a cell per substep, so building once at the start of the substep and using it for that substep's contact solve is safe. If your particles have different radii, make the cell as large as the largest diameter; if you query a larger radius (for fluid kernels, say), make the cell that radius, so the 3×3 block still covers it.

What the speed-up really is

At 2,000 settled particles the demo reports about 17,000 pair tests per substep with the hash, against 1,999,000 for brute force: about 117 times fewer. Of those 17,000, about 9,100 (4.5 per particle, close to the estimate of five) come from the 3×3 blocks themselves; the rest are hash collisions, which a larger table would reduce.

The measured time drops by much less than the test count, about ten times when this chapter was written. Each hash test costs more than a brute-force test: there is the build, nine hash computations per particle, and scattered memory reads, while brute force reads memory in order. The asymptotic win is real, though: at 20,000 particles the brute-force count grows a hundredfold and the hash count only tenfold. Always measure both the operation count and the time, because they tell you different things.

Capsules against capsules

Ropes and chains are often collided as chains of capsules, one per segment. Two capsules touch when the distance between their segments is less than the sum of their radii. In 2D there is a shortcut: two segments that do not cross reach their minimum distance at an endpoint of one of them, so the distance is the smallest of four point-to-segment distances, each the closest-point projection from above:

function segmentSegmentDistance(a, b, c, d) {   // 2D, segments a-b and c-d
  if (segmentsCross(a, b, c, d)) return 0;
  return Math.min(pointSegmentDistance(a, c, d), pointSegmentDistance(b, c, d),
                  pointSegmentDistance(c, a, b), pointSegmentDistance(d, a, b));
}
// overlap when segmentSegmentDistance(...) < r1 + r2; the normal joins the two closest points

In 3D, skew segments reach their minimum in the middle of both, and you need the general closest points between two segments: solve a 2×2 linear system for the two line parameters, then clamp them carefully (Christer Ericson's Real-Time Collision Detection, section 5.1.9, gives the standard robust version). Either way, the contact normal is the direction between the two closest points and the depth is $r_1 + r_2$ minus their distance.

For the broad phase of capsules, put each capsule's bounding box into the same spatial hash, inserting it into every cell its box covers. The structure does not care what shape is in the cells.

Tunnelling

Everything so far checks for overlap at the end of each step. Between steps, nothing is checked. A small object moving fast can be on one side of a thin wall at one step and on the other side at the next, and the simulation never sees an overlap. This is tunnelling, and it is the reason bullets in games pass through fences.

Switch the demo to "fast balls vs thin wall". Twenty balls of radius $r = 2$ cm fly side by side at the same speed towards a wall of thickness $t = 1$ cm. Their starting positions are staggered by a twentieth of one substep's travel each, so between them they sample every possible timing relative to the wall. Blue balls were stopped; red ones got through. The grey dots behind each ball mark the positions the simulation actually visited, one per substep.

Predicting when it happens

Let $s = |\mathbf{v}|h$ be the distance a ball moves in one (sub)step, and let $L = r + t/2$ be the distance from the wall's middle to the ball's centre at the moment of first touch. Measure the ball's penetration $p$ at the first step on which it overlaps the wall. Because the timing is staggered, $p$ is spread evenly between 0 and $s$.

Two things can go wrong.

  1. If $p \ge L$, the ball's centre landed past the middle of the wall. The SDF does what it is told: it reports the nearest surface, which is now the far face, and the push-out sends the ball through.
  2. If $p < L$, the ball is pushed back to touching the near face. But the PBD velocity update computes the velocity from where the ball came from, $s - p$ away, so it still points into the wall. On the next step the ball penetrates by $s - p$, and if that is $L$ or more, case 1 happens one step late.

The ball is stopped only if $s - L < p < L$. With $p$ spread evenly over $[0, s)$, the fraction of balls that tunnel is

$$f = \begin{cases} 0 & s \le L, \\ 2 - 2L/s & L < s < 2L, \\ 1 & s \ge 2L = 2r + t. \end{cases}$$

Two speeds stand out. Tunnelling begins at $|\mathbf{v}| = (r + t/2)/h$ and is certain from $|\mathbf{v}| = (2r + t)/h$: when the ball moves more than its own diameter plus the wall's thickness in one step. For a 2 cm ball and a 1 cm wall at 60 steps per second, $L = 2.5$ cm, so tunnelling begins at 1.5 m/s and every ball gets through at 3 m/s. That is a gentle throw of a table-tennis ball.

The demo runs eight substeps by default, so $h = 2.08$ ms and the two speeds are 12 and 24 m/s. At the default 16 m/s, $s = 3.33$ cm and $f = 2 - 5/3.33 = 0.5$: the formula says ten of the twenty balls tunnel, and the readout agrees. The panel shows both the prediction and the count, so you can check any speed you like.

Defence 1: smaller steps

Both thresholds are proportional to $1/h$, so $n$ substeps raise them $n$-fold. This is the bluntest tool, and often the right one, because substeps also help stiffness and convergence (the substepping chapter). But the cost grows with $n$ and there is always a faster object.

Defence 2: speculative contacts

The idea is to detect the contact before it happens. At the start of the step, while the ball is still in front of the wall, look for surfaces within the distance it could travel this step. If the gap $g_0 = \phi(\mathbf{x}_0) - r$ is less than the margin $|\mathbf{v}|h$, remember the surface as a plane, with the normal $\mathbf{n}$ and distance $\phi(\mathbf{x}_0)$ measured at the start. Then, after the prediction, enforce that plane, not the SDF at the predicted position:

$$C(\mathbf{x}) = \mathbf{n}\cdot(\mathbf{x} - \mathbf{x}_0) + \phi(\mathbf{x}_0) - r \;\ge\; 0.$$

However far past the wall the prediction lands, the plane is on the correct side, and the projection puts the ball back in front of it. If the ball would not have reached the wall, $C$ stays positive and nothing happens: the contact was only speculative. Tick "speculative margin" in the demo and no ball gets through at any speed.

The price is a slightly larger contact list, and an occasional ghost contact: a particle sliding fast past the corner of a box can be stopped by the plane of a face it would have missed. Engines that rely on speculative contacts keep the margin small and clip it to the actual motion. Ours also keeps only one plane per particle, which is fine for a ball and a wall but not for a corner.

Defence 3: swept tests

Continuous collision detection (CCD) asks for the time of first contact along the motion, instead of overlap at the end. For a ball moving from $\mathbf{x}_0$ to $\mathbf{x}_1$ towards a plane, the gap changes linearly along the motion, from $g_0$ to $g_1$, so the time of impact as a fraction of the step is

$$\tau = \frac{g_0}{g_0 - g_1}, \qquad \text{if } g_0 \ge 0 > g_1.$$

Move the ball to $\mathbf{x}_0 + \tau(\mathbf{x}_1 - \mathbf{x}_0)$, resolve the contact, and continue with the rest of the step. Against a general SDF, conservative advancement does the same job: the ball can safely move by its current gap $\phi(\mathbf{x}) - r$ without hitting anything, so advance by that, re-evaluate, and repeat until the gap is tiny or the step is used up. SDFs make this almost free, which is one more reason to like them.

Swept tests are exact but expensive and fiddly for rotating bodies and for many simultaneous contacts, so most real-time engines apply them only to objects flagged as fast. For position-based solvers the speculative margin is usually the better fit, because it slots into the same constraint loop as every other contact.

Thin and fast is the dangerous combination. Tunnelling depends on the ratio of the distance per step to the size of the objects involved. Thick floors and big particles hide the problem; a single thin wall, a cloth, or a rope made of small particles reveals it. When something falls through the world, compute $|\mathbf{v}|h$ and compare it with $r + t/2$ before suspecting anything else.

Hint: the sign of the push

Solution

function sdCapsule(px, py, ax, ay, bx, by, r) {
  const abx = bx - ax, aby = by - ay;
  let t = ((px - ax) * abx + (py - ay) * aby) / (abx * abx + aby * aby);
  t = Math.max(0, Math.min(1, t));                 // closest point on the segment
  const qx = ax + t * abx, qy = ay + t * aby;
  return Math.hypot(px - qx, py - qy) - r;
}

function collideSdf(i) {
  const d = sceneSdf(x[i], y[i]) - radius;
  if (d >= 0) return;
  const nn = sdfNormal(x[i], y[i]);
  x[i] -= d * nn.x;
  y[i] -= d * nn.y;
}

Solution 
function buildHash() {
  cellStart.fill(0);
  for (let i = 0; i < n; i++)
    cellStart[hashCell(Math.floor(x[i] / cellSize), Math.floor(y[i] / cellSize))]++;
  let start = 0;
  for (let h = 0; h < TABLE_SIZE; h++) { start += cellStart[h]; cellStart[h] = start; }
  cellStart[TABLE_SIZE] = start;
  for (let i = 0; i < n; i++) {
    const h = hashCell(Math.floor(x[i] / cellSize), Math.floor(y[i] / cellSize));
    cellStart[h]--;
    cellEntries[cellStart[h]] = i;
  }
}

function forEachHashNeighbour(i, visit) {
  const ix = Math.floor(x[i] / cellSize), iy = Math.floor(y[i] / cellSize);
  for (let dx = -1; dx <= 1; dx++)
    for (let dy = -1; dy <= 1; dy++) {
      const h = hashCell(ix + dx, iy + dy);
      for (let k = cellStart[h]; k < cellStart[h + 1]; k++) visit(cellEntries[k]);
    }
}

Solution 
function findSpeculativeContact(i, h) {
  specOn[i] = 0;
  const margin = Math.hypot(vx[i], vy[i]) * h;
  const d = sceneSdf(x[i], y[i]);
  if (d - radius < margin) {
    const nn = sdfNormal(x[i], y[i]);
    specOn[i] = 1; specNx[i] = nn.x; specNy[i] = nn.y; specD[i] = d;
  }
}

function solveSpeculativeContact(i) {
  if (!specOn[i]) return;
  const C = specNx[i] * (x[i] - px[i]) + specNy[i] * (y[i] - py[i]) + specD[i] - radius;
  if (C < 0) { x[i] -= C * specNx[i]; y[i] -= C * specNy[i]; }
}

In the pouring scene the fastest particles fall at about 6 m/s, which with eight substeps is 1.3 cm per substep. For the 4 cm thick slopes, $r + t/2 = 1.2 + 2 = 3.2$ cm, so nothing can tunnel and the margin has nothing to prevent.

grids, bins and level sets in MPM

The uniform grid of this chapter comes back in every MPM chapter, promoted from an acceleration structure to the place where the physics happens. The MPM course notes describe obstacles as level sets, which is another name for an SDF: the solver evaluates $\phi$ at grid nodes or particles, takes the normal from $\nabla\phi$, and removes the velocity component that points into the obstacle. On the GPU, the PB-MPM code sorts its particles into tiles of grid cells with the same count, prefix-sum and insert passes you wrote for buildHash, so that each thread group can work on one tile's particles.

Summary

  • Collision detection has a broad phase (cheap, conservative, produces candidate pairs) and a narrow phase (exact test, produces normal and penetration depth).
  • A signed distance function gives inside/outside, depth and, through its gradient, the normal. Circles, half-planes, boxes and capsules each take a few lines; a union is a min.
  • Particle against scene: gap $g = \phi(\mathbf{x}) - r$; if $g < 0$, move by $-g\,\mathbf{n}$. It is a PBD inequality constraint.
  • The closest point on a segment (project, clamp) gives the capsule SDF and capsule-capsule contacts.
  • A spatial hash with cell size equal to the particle diameter, filled by a counting sort and queried over 3×3 cells, turns $O(n^2)$ pair tests into $O(n)$. The time saved is smaller than the tests saved.
  • Tunnelling starts when a ball moves more than $r + t/2$ per step and is certain beyond $2r + t$. Defences: substeps, speculative contacts with margin $|\mathbf{v}|h$, and swept (continuous) tests.

Verifying a Simulator

How to know your simulation is right, rather than merely plausible.

A simulation that looks right can be wrong in a hundred ways. A pendulum that swings a little too slowly, a rope that sags a few percent too much, damping that is twice what you typed in: none of these are visible, and all of them will mislead anyone who uses the numbers. Worse, a bug and a coarse time step produce the same symptom, "the answer is a bit off", and you cannot tell them apart by looking.

This chapter is about the discipline that tells them apart. It rests on a few simple ideas: compare against problems whose answer you know exactly, run every comparison at several step sizes so that the trend separates discretisation error from mistakes, check the quantities physics says cannot change, and turn all of it into automatic tests with tolerances you can defend.

By the end you will have built a convergence study that measures the order of accuracy of an integrator from a log-log plot, written a catenary test for a position-based chain and found the tolerance it actually meets, and seen which kind of test catches which kind of bug.

Verification and validation

Two words that sound alike and mean different things:

  • Verification asks: are we solving the equations right? Given the model you wrote down (Newton's laws, an inextensible chain, a linear spring), does the code compute its solution, with errors that shrink the way the numerical method promises? This is mathematics and software, and it can be settled on a computer.
  • Validation asks: are we solving the right equations? Does the model describe the real rope, the real rubber, the real fluid? That needs measurements of the real thing, and no amount of programming can replace them.

Verification comes first. If the code does not solve its own equations correctly, comparing it with experiments tells you nothing: a good match might be two errors cancelling. This chapter is about verification. Validation is a topic for the lab, but its first step is the same honest bookkeeping.

Convergence: the slope is the order

A single comparison with a closed form is not enough. Suppose your pendulum is 0.2% off after two seconds. Is that a bug, or simply what a time step of 10 ms costs? You cannot know from one number. Run it again with half the step.

Every integrator in this course has an order of accuracy $p$: for small enough $h$, the error after a fixed time $T$ behaves like

$$e(h) \approx C\,h^p \quad\Longrightarrow\quad \log e = \log C + p \log h.$$

On a log-log plot of error against step size, that is a straight line with slope $p$. Halving $h$ divides the error by $2^p$: by 2 for a first-order method, by 4 for second order, by 16 for fourth. That slope is the most powerful single test you can run on an integrator, because a correct implementation must produce it and almost any bug destroys it.

The procedure:

  1. Pick a test problem and a final time $T$. Here a pendulum of length 1 m released from 1 rad, and $T = 1.7$ s.
  2. Get the exact answer at $T$. The pendulum at 1 rad has no elementary closed form, so use a reference solution: the same problem solved with a much more accurate method and a tiny step (RK4 with 40,000 steps, whose error is far below anything we will measure). For the spring, use the closed form.
  3. Run with $N = 10, 20, 40, \dots, 10240$ steps, $h = T/N$, and record the error $|q_N(T) - q_\text{ref}(T)|$.
  4. Fit a straight line to $\log e$ against $\log h$ over the finest points that are still above round-off, and read off the slope.
function convergenceStudy(name) {
  const ref = exactOrReference(), points = [];
  for (let k = 0; k <= 10; k++) {
    const N = 10 * Math.pow(2, k);
    const [q] = runTo(name, acc, q0, 0, T, N);
    points.push({ h: T / N, err: Math.abs(q - ref) });
  }
  return points;
}

Choose an integrator and read the measured order. For the pendulum the fits come out as 1.10 (explicit Euler), 1.00 (symplectic Euler), 2.00 (midpoint, also called RK2), 2.00 (velocity Verlet) and 4.00 (RK4). The plot shows more than the number:

  • The asymptotic range. Explicit Euler's line bends: at large steps its error is dominated by its energy growth, and it only approaches slope 1 below about a millisecond. Fit over the coarse points and you would measure about 1.6, and wrongly conclude the method is better than it is. Always look at the plot, not only the fit.
  • The round-off floor. RK4's error falls sixteenfold per halving, all the way down to about $10^{-15}$ at the finest step. That is close to the limit of double precision (about 16 significant digits, and every step adds a little rounding). One more halving and the error would stop falling: points on that floor say nothing about the method, so the fit ignores errors below $10^{-11}$.
  • Where you look matters. The comparison time $T = 1.7$ s is deliberately not a turning point. The pendulum's period is 2.14 s, so it is caught mid-swing, about 0.79 of a period in. At a turning point the position is insensitive to a small phase error (the slope of the cosine is zero there), and a first-order phase error shows up as a second-order position error: the method appears more accurate than it is. Compare where the solution is moving, or compare the whole state $(q, v)$.

Several step sizes separate the two kinds of error. Discretisation error shrinks with $h$ at the predicted rate. A bug, or a modelling mistake, does not. If the error stops shrinking as $h \to 0$, the code converges to the wrong answer, and no time step will fix it. If it shrinks at the wrong rate, the method is not implemented as you think.

Conservation checks

Some quantities cannot change, whatever the step size: the energy of an undamped, unforced system, the momentum of a system with no external forces, its angular momentum if there are no external torques either. Each gives a test that needs no closed form at all.

The trick is to know what the integrator is supposed to do, which is often not "conserve exactly". For the undamped spring $q'' = -\omega^2 q$ the step matrices of the time integration chapter give the exact energy factor per step, with $x = h\omega$:

The demo's energy test runs the spring ($\omega = 2\pi$ rad/s) for 100 s at $h = 0.01$ s and compares the drift of the energy, averaged over the first and the last period to remove the bounded wobble of the symplectic methods, with the prediction for the chosen integrator. That is a sharper test than "energy is roughly conserved": it fails if explicit Euler gains energy any faster or slower than theory says, and it fails if a symplectic method starts to drift.

Regression tests with tolerances

Once a check works, make it automatic: a function that runs a small scenario, compares one number with its expected value, and reports pass or fail. Run all of them after every change. That is a regression test: it exists to catch the day something that used to work stops working.

The art is the tolerance. Too tight, and the test fails on harmless changes (a different order of floating-point additions). Too loose, and it passes broken code. Derive it: from the order of the method and the step size (explicit Euler's error at $h = 1$ ms on the damped spring is about $3 \times 10^{-3}$, so a tolerance of 0.01 passes it with margin), or from a measured study like the ones in this chapter, with a safety factor written next to it. The demo runs three:

  1. order of accuracy: the measured slope is within 0.2 of the integrator's order;
  2. energy drift: the undamped spring's drift after 100 s matches the theory above within $10^{-4}$ plus 1%;
  3. damped decay: a damped spring ($\zeta = 0.1$, $\omega = 2\pi$ rad/s) at $T = 1.7$ s with $h = 1$ ms is within 0.01 of the closed form $x(T) = -0.1558$.

Testing a constraint solver: the catenary

The same ideas apply to position-based solvers, where the step size is joined by two more numbers: the resolution (how many links) and the iteration count. A chain of total length $L$ hanging between two pins a distance $s$ apart settles on a catenary $y = a\cosh(x/a) + c$, where $a$ (the ratio of the horizontal tension to the weight per unit length) is fixed by the length:

$$L = 2a \sinh\frac{s}{2a}.$$

For $L = 2$ m and $s = 1.6$ m, bisection gives $a = 0.6764$ m and a sag of 53.09 cm. The catenary demo hangs a chain of $N$ equal links from the two pins, starting as a V so that the solver has work to do, lets it settle for 15 simulated seconds, and measures the largest vertical distance between the nodes and the catenary.

With 50 Gauss-Seidel iterations per substep the table reads 2.90 mm (0.55% of the sag) for 10 links, 1.05 mm (0.20%) for 20, 1.85 mm (0.35%) for 40, and 7.04 mm (1.33%) for 80. More links make it worse. Two errors are adding up:

  • Discretisation. A chain of point masses joined by straight links is not a continuous chain. Its exact equilibrium can be computed by hand (each node adds its weight to the vertical tension), and it differs from the catenary by 2.85, 0.71, 0.18 and 0.044 mm for 10, 20, 40 and 80 links: a factor of 4 per doubling, second order in $1/N$.
  • Solver error. Gauss-Seidel on a chain converges more slowly the longer the chain (its convergence factor is roughly $1 - c/N^2$, from the solvers chapter), so at a fixed iteration count a finer chain is left stretched. The table's stretch column shows it: 0.002% for 10 links, 0.58% for 80.

At 10 links the solver has converged and the measurement, 2.90 mm, sits on the discretisation error of the exact discrete chain, 2.85 mm. That agreement is the verification: the solver computes the discrete model's answer, and the discrete model approaches the continuous one at the rate it should. At 80 links even 300 iterations leave 1.16 mm, dominated by the solver. So "what tolerance does this chain meet?" has an honest answer only together with its resolution and iteration count: here 0.2% of the sag with 20 links and 50 iterations, and no better than 1.3% with 80 links at the same cost.

Reporting honestly

Verification ends in a report, and a useful one states what was not achieved as clearly as what was. "The pendulum is second-order accurate" is a claim; "measured order 2.00 over $h$ from 1.3 to 0.17 ms, error $5 \times 10^{-8}$ rad at $h = 0.17$ ms" is evidence. When a target is missed, say so, with the number: "the 80-link chain meets 1.3% of sag with 50 iterations, not the 1% target; it needs about 70". A missed target with a number attached is a known limitation. A missed target rounded into a pass is a bug waiting for someone else.

Hint: the least-squares slope

With $x_i = \log_{10} h_i$, $y_i = \log_{10} e_i$ and $n$ points, the slope of the best straight line is $b = (n \sum x_i y_i - \sum x_i \sum y_i)/(n \sum x_i^2 - (\sum x_i)^2)$.

let sx = 0, sy = 0, sxx = 0, sxy = 0;
for (const p of use) {
  const x = Math.log10(p.h), y = Math.log10(p.err);
  sx += x; sy += y; sxx += x * x; sxy += x * y;

return (use.length * sxy - sx * sy) / (use.length * sxx - sx * sx);

Summary

  • Verification checks that the code solves its equations correctly; validation checks that the equations describe reality. Verify first.
  • Keep a library of closed-form tests: free flight, springs with and without damping, the pendulum, the catenary, the cantilever, the capstan, Laplace's law.
  • A convergence study plots error against step size on log-log axes; the slope is the order (1 for explicit and symplectic Euler, 2 for midpoint and velocity Verlet, 4 for RK4). Fit only the asymptotic range, above round-off, and compare away from turning points.
  • Error that stops shrinking as $h \to 0$ is a bug or a modelling error, not discretisation.
  • Conservation checks are sharpest when compared with what the integrator is supposed to do, not with "exactly conserved".
  • Automate checks as regression tests with derived tolerances; use several integrators, problems and resolutions; and report unmet targets with their numbers.
